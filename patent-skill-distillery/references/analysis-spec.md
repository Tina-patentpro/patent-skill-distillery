## 1. 目标知识问题表（第 0 步必答，写入 logs）

每个选题在「输入/输出/边界」之外，先回答六类问题：

| # | 类别 | 问什么 | 示例（claim-drafting） |
|---|---|---|---|
| Q1 | 概念区分 | 哪些概念容易混，边界在哪 | 独立权利要求 vs 必要技术特征 |
| Q2 | 判断选择 | 什么情境下选什么做法 | 装置 claim vs 方法 claim |
| Q3 | 条件例外 | 规则的适用条件与例外 | 「其特征在于」用法与限制 |
| Q4 | 方法操作 | 步骤怎么做、顺序为何 | 前序部分写法流程 |
| Q5 | 失败修正 | 常见错误与修正 | 上位不当导致缺支持 |
| Q6 | 依据与不确定性 | 结论依据是什么，哪些没把握 | 指南 2025 修改对 AI 相关撰写的影响 |

**这张表既指导取料，也指导验收。** 最终报告必须区分四态：

- ✅ 已回答（有依据支撑）
- 🟡 部分回答（有材料但不完整）
- ⚪ 资料不足（读了但没提取到——**不得解释为"来源中不存在"**）
- ❓ 未读不能判断（该材料根本没读）

四态结论与 §2B 知识问题覆盖记录对齐。

## 2. 知识条目（第 2 道核心）

**禁止从来源文件直接生成 Wiki 或 Skill。** 每个纳入产物的关键结论先形成知识条目，存 `C:\Users\<user>\.workbuddy\skills\knowledge\entries\<skill-name>\<主题>.entries.md`。

**条目 = 能被单独引用、比较、验证、更新的最小完整知识单元。** 结论+成立条件+关键例外是一个整体，不为体积拆散。

### 条目 Markdown 模板（v3.1：中性句式 + 三标签 + 证据状态三子项）

```markdown
### [KE-<主题>-<序号>] <一句话标题>
- **原规则 ID**：<来源的规则 ID 原样保留；无则"—"；来源体系里未定义的标签标「待解释」，不自行映射丢弃> ｜ **来源版本**：<文件版本/法条版本>
- **核心命题**：在<前提/适用情境>下，<对象><按原文的陈述方式给出结论/关系/做法>；关键例外<…>
- **原始依据**：<raw 文件路径 或 ima 库+media_id> §<章节/段落>
  > <支持命题的必要原文片段（关键句原文，非转述）>
- **三标签**（三项分离记录，不得互相替代、不得合并简化）：
  - 知识性质：<概念/事实/规范/经验策略/方法步骤/案例观察/反例/执行要求——这条知识是什么>
  - 原始标签：<来源自带的 H/P/S/A/G/OA 原样保留；H/P/S/A 不作简单强弱排序理解>
  - 原文情态：<必须/应/宜/可/通常/事实陈述——原文怎么说的就怎么记>
- **适用边界**：适用=<…>；不适用=<…>；限定=<法域/时间/程序阶段>；未知=<明确列出未知项>
- **形成方式**：原文直载 / 结构化重述 / 跨源归纳 / 本轮新设计
- **证据状态**（三子项）：
  - 支持情况：<直接支持 / 间接支持 / 暂无>
  - 相反证据：<未发现 / 已发现（附条目 ID）/ 未检查>
  - 核验状态：<未核验 / 部分核验（范围）/ 已核验（范围）>
- **条目状态**：<已提取 / 待核验 / 允许解释性展示 / 允许执行使用 / 已被替代>
- **图表证据**：<本条目涉及的独立图片/文档内图片是否已静态读取；未读/不可读记录于此>
- **产物去向**：Wiki=<主题>；Skill=<判断节点名>；案例=<patterns 哪篇>；测试=<哪些用例>
- **分析依据摘要**：<跨源归纳与本轮新设计条目必附五要素，见 §2A；其余路线可省>
```

### 【v3.1.3；v3.1.5 升 schema 1.2】`ke-meta` 机读元数据块（条目内）

在条目末尾（修订说明之前）追加一个围栏块，作为**机读契约**，供构建器与验证器读取：

```markdown
- **结构化元数据**：<!-- 与上方命题冲突时以命题为准，并须当次修好 -->
  ```json ke-meta
  {
    "use": ["解释引用"],
    "scope": "<该记录作用命题（非适用边界全文）>",
    "source_synthetic": false,
    "deps": [
      {"to": "KE-<主题>-<序号> rN", "purpose": "必要知识|背景解释|验证证据", "required": true,
       "claim_scope": "<可选；子命题级作用域（如「子命题①」）。缺省=记录级>"}
    ],
    "open_layer": {
      "question": "<本条唯一未决问题>",
      "candidates": ["<候选一>", "<候选二>"],
      "status": "unresolved",
      "resolution_account": "<该未决项由哪本账闭合；与哪些账分账>",
      "must_not": "<下游硬约束：未决状态不得被覆盖；内部解释不得冒充来源>",
      "internal_decision_scope": "<内部决策的效力边界>"
    }
  }
  ```
```

约定（缺一即算结构缺陷，除 `deps` 可为空数组）：
- `use` 多值，枚举 {解释引用, 内部可推翻策略, 正式事实依据}；**声明「正式事实依据」须核验状态为外部已核**（内部约定不得充当外部事实）
- `scope` 非空；`deps[].to` **只接受 `KE-ID rN`（含修订号）或显式类型标记 `type: <名称>`**——「产品执行需要」这类不可解析表述一律报错
- `deps[].purpose` 决定该依赖是否影响结论成立；`required` 为布尔
- `source_synthetic` **三态**（true / false / **null=未知**）；null **不得**按 false 处理
- 依赖方向与正文一致；**背景互链（purpose=背景解释, required=false）是合法关系**，不计作独立支持、不套用知识证据循环规则（不得因成环而误拒绝）
- **`claim_scope`（v3.1.5 新增，schema 1.1→1.2）**：**可选**，只用于 `purpose=必要知识` 的条目；声明后该必要依赖**只作用于所列子命题**——其缺失/未知**不得**把**无关子命题**连带拖成 unknown（防「记录级 required=true」与「必要知识缺少则结论=未知」联立造成误传播）。缺省=记录级
- **`open_layer`（v3.1.5 新增，schema 1.1→1.2）**：未决层**结构化登记**（不是正文散述）。`status` 枚举 {unresolved, resolved}；`candidates` 为非空数组；`must_not` 为**下游硬约束**——引用方必须原样传递未决状态与全部候选；`resolution_account` 与策略效果账**分账**，任一未完成不得用另一账替代
- **`purpose` 为闭枚举**（v3.1.5 明确）：不得新增值。「关联 QC 约束」这类需求以**删除该 dep** 满足，零 schema 变更（R4 双账分列）


### 【v3.1.1】条目内四类内容区分（F04）

每个将被下游使用的条目，其内容必须能区分四类，各自有应去的记录位置——**模型自己的判断不得混入支持证据**：

| 内容 | 记录方式 |
|---|---|
| 来源确实写了某句话 | 来源主张（附原文引述，进「原始依据」） |
| 本轮对原文的解释 | 解释结论（附解释依据，进「分析依据摘要」） |
| 已从其他材料核实的事实 | 外部核验结果（附**具体可定位来源**，进「核验状态」） |
| 模型认为可能成立的判断 | 待验证假设（进「未知」或独立候选条目，**不计入支持证据**） |

- 「与通行理解一致」不得作为间接支持登记；有价值时保留为解释或待验证假设
- 法源指代（如「26.4 条」）先解析法名/条/款/版本再绑定，解析不了就登记待解析项，不得先行绑定法源名称
- 外部否定结论（「非规范原文」「无此规定」）须附规范原文比对，否则不登记

### 【v3.1.1】反证引用精确化（F04）

相反证据必须指向**精确条目 ID + 具体命题**；禁止「附近」「同上」等跨对象作证。引用前核对被引条目实际讨论的对象（例：图件优先级策略 ≠ 编号规范）。

### 【v3.1.1】条目拆分条件（F04）

**能够独立变化、适用范围不同，或核验状态不同的命题，应拆为独立条目或可单独引用的子命题**（不机械按句拆）；结论、成立条件和关键例外仍一起保留。拆分时保留原 ID → 新条目/子命题的对应关系并更新实际引用方，不得删除重写。目的：避免「其中两项已核验」被读成「整条规则已核验」。

### 中性句式规则（v3.1，替代统一「应」句式）

1. 核心命题**不预设强度**：原文是事实保留事实陈述，是建议保留建议，是案例观察保留观察；**只有原文在其声明的适用范围内确有该情态（法条/指南/审查规程类）才用「应/必须/不得」**【v3.1.1：不限法条字样，改为「来源声明的适用范围内确有该情态」】
2. 「来源表达了结论」≠「结论正确、现行、适用于本任务」——分别由证据状态、来源版本、适用边界承载
3. 跨源归纳的条目：**每个前提分别列来源及支持范围**（哪个前提单源、哪个多源）

### 条目 ID 与修订

- 格式：`KE-<主题码>-<三位序号>`（如 KE-CLM-001、KE-DRW-014），跨文件引用一律用条目 ID
- 同一 KE 修改后**保留身份**，修订号 +1（记作 KE-CLM-001 r2）；`_index.md` 记录当前修订号与历史；修订以追加修订记录方式落地，r1 原文不删改
- 一条知识允许多工序引用，不复制多份各自漂移；**多 Skill 共用条目放 `C:\Users\<user>\.workbuddy\skills\knowledge\entries\_shared\`**，单一维护归属，其他 Skill 引用不复制

### 条目状态生命周期

`已提取 → 待核验 → 允许解释性展示（入 Wiki）／允许执行使用（入 Skill）→ 已被替代`

**允许 Wiki 展示争议 ≠ 批准把争议一方作为执行规则**——执行使用需另过 Skill 准入门（§7）。批准版本记录在 `_index.md`（快照号+日期）。

【v3.1.1】生命周期与使用方式分开表达，**不新增状态名**：「内部设计候选·仅预览」「策略说明·候选建议」等用「生命周期=候选/待核验 + 使用方式记录」组合表达，不造新本体状态。

### 要点

1. 原料先落 `raw\`（带溯源块），条目从中提炼——原始依据字段必须能定位回 raw 文件
2. 四层分析深度分开标注：直接抽取（不改原意）/ 结构化重建（说明各部分来源，新组织方式不冒充原文）/ 跨源归纳（给支撑材料+归纳范围+保留反例）/ 新方法建议（标「本轮设计·待验证」，不得冒充既有事实或 H 级规则）
3. 【v3.1.1】**来源许可与本轮生成策略分开**：来源原文表达的许可/要求原样保留为来源主张；为执行效果提出的新策略另行登记为本轮设计（依据/预期作用/适用边界/失败条件/试验方式），不得互相冒充

## 2A. B 路线分析七动作 + 三推理铁则（原始材料蒸馏必走）

B 路线不是把原文抄进条目，而是完成以下动作（顺序执行，结果体现在条目字段与分析依据摘要中）：

1. **还原问题与情境**：材料在回答什么问题，结论在什么前提情境下成立
2. **拆分陈述角色**：每段内容分别标为 事实 / 定义 / 结论 / 理由 / 建议 / 案例 / 例外
3. **重建判断依据**：结论依赖哪些前提；哪些前提有材料支持、哪些没有
4. **找出决定性条件**：哪些条件变化会改变结论（→ 写入适用边界）
5. **检查可推广程度**：单案例事实 / 特定情境方法 / 有明确适用范围的规则——三档不同处理
6. **跨源综合**：围绕**同一知识问题**（问题表 ID）比较多源材料，不是逐条判重。【v3.1.1】综合不止于「同义/补充/冲突」关系标签，围绕一个知识问题形成**完整回答**：已确认共同结论 / 条件化分支 / 尚未解决的差异 / 需补充的证据 / 对 Wiki 与 Skill 的不同影响
7. **决定产物形态**：解释 / 条件化规则 / 案例 / 候选方法（待验证）/ 保留缺口（按四态作答）

【v3.1.1】**跨源综合范例 · 编码规则六步执行能力**（F02，来自审计报告第五.3）：两份材料编码口径不一致时，可复用的产出不是「改写成一段话」，而是六步能力：识别编码体系 → 核对对象层级 → 检查命名空间冲突 → 生成编号 → 校验唯一性与引用关系 → 输出未决映射。体系未确认前**只交付差异表与候选映射**，暂停最终编号分配，不采用「文件名有优化版即覆盖」或「正文有版本号即全局优先」任一捷径。

【v3.1.1】**跨源专门对照**（F02）：除概念主题聚类外，对**标识符、单位、字段名、枚举、数量、时间、角色、对象**建立专门跨源对照表；每条建议可执行的编码/映射规则至少经一组**输入—输出样例 + 冲突样例**验证。

**三推理铁则**（违反任一即返工）：

1. **必要条件 ≠ 充分条件**：「要 B 需要 A」≠「有 A 就能 B」
2. **先后发生 ≠ 因果成立**
3. **出现共同做法 ≠ 只能这样做**（行业惯例不是规范）

**分析依据摘要**（五要素，跨源归纳与本轮新设计条目必附；是可审查的论证摘要，不是过程流水账）：

已确认前提 / 对应来源 / 关键推导依据 / 结论适用范围 / 相反材料或未解决缺口。

**「保持原规则不变」是合法高质量结果**：分析后确认既有规则无需修改，与发现新规则同等记入成果，不为产出深度强行翻案。

## 2B. 覆盖记录（两类，轻量）

不要求每段材料都做卡，但**每轮蒸馏结束必须能回答「覆盖了什么、没覆盖什么」**：

**知识问题覆盖**（按问题表作答）：

| 问题 ID | 已读材料范围 | 支撑条目 | 未解决部分 | 四态结论 |
|---|---|---|---|---|

**来源处理覆盖**（按来源交代）：

| 来源+版本 | 实际读取范围 | 处理结果 | 未读/不可读/排除/暂缓及理由 |
|---|---|---|---|

规则：

- 抽样结论**只对声明的抽样范围负责**；未覆盖部分不得默认已审阅
- 有限集合清单（如 40 创新原理、检查表条目）**须全量核对**；大量案例可有目的抽样——**两者不得混用**
- 未读/不可读/排除都记理由，与四态里的「未读不能判断」对齐

【v3.1.1】**版本提取与计数可复算**（F07）：

- 版本号先查**正文/修订记录/元数据**，文件名只作兜底；溯源块与正文版本不一致时记**元数据冲突**，不得静默覆盖
- 有限集合核对**输出结构化成员清单**（集合定位/实际成员/期望成员/缺失/重复/未识别），**数目由解析汇总，模型不得手写「全量核对 N 项」**；计数、查重、比对适合用代码完成，代码做机械部分、模型做语义判断，不互相替代

【v3.1.1】**阅读覆盖 vs 使用覆盖**（F07）：未深处理但被用于决定执行行为的规则，不得仍归为「完全未覆盖」；排除列表、条目来源、消费者三者应可对照（哪条规则进了哪个节点、依据哪个条目，可反查）。

## 2C. 【v3.1.3】三种分析对照 + 精确读取 + 错误处理路径（新增）

### 2C.1 三种分析对照（对应 A/B/C 三路线，**判据不得混用**）

| 对照 | 适用路线 | 比什么 | 判据 | 记录去向 |
|---|---|---|---|---|
| **① 移植对照** | A（成品规则库/规则卡/判断链） | 成品规则 **vs 原始来源原文** 逐句 | 可迁移／需重组／依据缺失／历史版本／描述型／实质错误（六分类，**失败按原因分流，不统一降级**） | 条目「分析依据摘要」+ 双门准入记录 |
| **② 重提对照** | B（原始材料） | 原始材料 **→ 七动作** → 条目，**与既有条目/既有答案隔离** | 七动作逐条落位；三铁则各拦截一处升格；**同一来源内部区分证据四层级**：原始案例/引文 → 作者解释 → 作者归纳 → 模型再解释 | 条目、覆盖记录两类表、独立性说明 |
| **③ 增量对照** | C（已有成熟技能） | 新版本 **vs 旧版本** | 差异落**六分类**；只蒸馏本地特有增量 | 增量记录 + 依赖分支影响分析 |

**禁止**：用对照①的结论替代对照②的证据（「成品说对了」不等于「从原始材料能独立重建这个结论」）；用同会话答案对照充当独立性证据（§8）。

### 2C.2 精确修订 / 用途 / 范围读取（v3.1.3 强制）

- **按修订读**：引用条目一律写 `KE-ID + rN`；构建器与验证器对**未标修订**的引用按「当前修订」解析并**在输出中显式标注**（如 `KE-DRW-027（未标修订·按当前修订解析）`），不静默。
- **按用途读**：`use` ∈ {解释引用, 内部可推翻策略, 正式事实依据}。「可执行」**不是**全用途授权——把内部约定条目用于「已核实外部法律事实的最终结论」属**越权**，验证器 QUAL-USE 直接拒绝。
- **按范围读**：`scope` = 该记录**作用命题**（不是适用边界全文）。依赖是否影响本次结论由 `purpose`（必要知识／背景解释／验证证据）决定：**背景解释不影响结论成立，必要知识缺少则结论=未知**。
- **未知只影响真正依赖它的结论**：同一记录内不同命题的未知**不得互相传染**（例：某记录「2025 修改影响对照=已核无影响」与「原规则依据核验=未核」须分开，只有依赖后者的结论才受影响）。

### 2C.3 错误处理路径（遇错停在哪、怎么改）

| 情形 | 处理 | **禁止** |
|---|---|---|
| 依赖目标不可解析（非 KE-ID 且无 `type:`） | **停在构建门前报错**，补类型标记或改指 KE-ID | 丢弃该边后宣称「无断链」 |
| 正文与 manifest 块散列不一致（漂移） | 以**实际文件**为准，触发重新构建 + 回归 | 以 manifest 为真；两处各留一份 |
| 同一 KE 出现多个当前修订 / 同号异文 | 阻断构建，回到条目库合并 | 「内容差不多」放行 |
| 来源合成性未知（`null`） | 按未知处理：可作其范围内**测试证据**，**不得**核实外部事实 | 把 null 当 false |
| 条目资格不足以支撑绑定的用途 | 降级为预览/建议输出，或止步 Wiki | 为保通过而放宽资格；**整批阻断** |
| 证据三子项任一为空 | 补齐后重建（支持方式／反证／核验状态**互不替代**） | 用「支持情况」填「核验状态」 |
| 结构错误为 0 | 仅表示结构合格 | 以「0 结构错误」证明关系已正确建模 |

## 3. 语义保真检查表 + 反向检查问题集（提取后必跑）



| 检查项 | 不合格示例 |
|---|---|
| 「应/宜/可/通常/仅当/至少/至多/除外」保留了吗 | 「通常采用 B」→「必须采用 B」❌ |
| 对象、数量、范围被扩大/缩小/省略了吗 | 「该情形下用 X」→「用 X」❌ |
| 顺序、条件、例外保留了吗 | 丢掉「除…外」❌ |
| 案例观察被升格为规范了吗 | 「案例用了 X」→「应使用 X」❌ |
| 「未发现」被改写为「不存在」了吗 | 「未发现直接依据」→「没有依据」❌ |

【v3.1.1】**反向检查问题集**（输出前自检追问，任一答不上即保留候选不提级）：

1. 引用实际支持到什么范围？（引用≠全文支持全文）
2. 有没有从**许可推义务**（允许保留→不保留即违规）？
3. 有没有从**条件推因果**（有 A 且有 B→A 导致 B）？
4. 有没有从**单例推通则**（一个案例→普遍规则）？
5. 相关定义与邻接限定是否已读（最小上下文回读，见 §4）？
6. 同名字段是否同一命名空间（TP-001 在两份材料里是同一对象吗）？

**零升格、零降格**是知识迁移门（§7 第一门）的硬性验收线。

## 4. 跨源七关系 + 判定规则（替代「冲突标两说」）

【v3.1.1】**情态不互换 + 最小上下文回读**（F01，判定前置规则）：

> **允许、要求、禁止和建议不得互相转换。**「允许采用 X」推不出「必须采用 X」，更推不出「不采用 X 即违反该条」。发现表面冲突时，先回读**同一来源中直接相关的定义、限定和相邻规则**（围绕会改变结论的最小相关上下文，不是重读整个库）；不得跳过相邻限定后再创造调和规则。无法确认冲突时记「**待解析差异**」，不为凑测试类型强行生成冲突或调和。

（固定测试：G-004「仅保留必要标号、步骤号、模块名」被 R1 遗漏、KE-DRW-025 曾由许可推义务——已固化为回归测试 T01。）

**来源关系（血缘）与命题关系（语义）分开记录**——同一对材料可两者兼有（既是同源转述、又在命题上构成补充）：

| 组 | 关系 | 处理 |
|---|---|---|
| 来源关系 | 同义重复 | 合并为一条，多来源并注 |
| 来源关系 | 同源转述 | 标共同出处，**不算多源验证** |
| 命题关系 | 补充 | 各自保留，条目互链 |
| 命题关系 | 特殊化 | 通用—特定关系，分别写明适用层 |
| 命题关系 | 条件不同 | 按下方六要素判定，**不得只看条件不同就排除冲突** |
| 命题关系 | 真冲突 | 同适用范围不兼容 → 保留争议+执行指引+待补证据清单，**不生成无条件执行规则** |
| 命题关系 | 替代失效 | 记录替代关系+历史版本（如指南 2023→2025） |

【v3.1.1】命题比较前先比**动作类型**：同现某个词（如「限缩」）不等于同一命题——「解释权利要求」与「修改权利要求」是不同动作，先分动作再比条件（T02）。

### 「条件不同」判定规则

先比较**六要素**：主体 / 对象 / 时间 / 适用范围 / 条件 / 约束方式。

- 范围**不重叠** → 分别保留，互链
- 范围**重叠且重叠部分要求不兼容** → 进**冲突或例外有效性分析**——B 可能是 A 的有效例外，而非「不冲突」；但例外存在本身**不产生**对方义务（见前置规则）

### 「发现反例」处理（先核验再分类，不得对所有反例统一缩边界）

先核验：反例**真实性 / 适用范围 / 反驳对象**。然后六情况：

1. 推翻事实性命题 → 撤销或改写条目
2. 证明原范围过宽 → 缩小适用边界
3. 落在原例外内 → 不影响原命题，补注即可
4. 不同情境 → 按「条件不同」六要素判定
5. 材料不可靠 → 进待核验区，暂不作反证
6. **只是违反规范的实例** → 不推翻规范本身，可作「常见违规警示」入案例

【v3.1.1】**逻辑反模型**（F03）：逻辑上可以构造的情境（「想象得出一种反例」）只能作为**逻辑反模型**——登记时必须说明**该模型满足哪些前提、使哪个结论不成立**；它可推翻必然推理，**不证明经验事实**（真实案例发生/处理效果验证属经验证据，须另行取得）。「真实性=场景逻辑成立」不得作为反例已核验的依据。

→ 再决定：维持 / 补解释 / 增例外 / 缩范围 / 撤销 / 转人工。**例外分支仅在判定需要时建立**【v3.1.1：不默认「发现反例→加例外分支」】。

### 两判断铁则

1. **相似 ≠ 重复**：差一个「仅适用于」限定就是两条规则
2. **来源多 ≠ 证据多**：本地笔记/公众号/已有 Skill 可能在转述同一份材料——追溯共同源头

## 5. 案例七段式（patterns 条目的标准结构）

初始情境 → 关键事实 → 判断依据 → 采取动作 → 可观察结果 → 适用边界 → 能否迁移。

案例文本缺过程/因果依据时，先作「模式候选/写法示例」入 patterns，**不当成熟通用规则**（不进 cheatsheet）。

## 6. Skill 产物：最小执行结构 + 未知传播（第 3 道）

### 判断节点五要素

| 要素 | 要求 |
|---|---|
| 看什么 | 输入事实与查找位置 |
| 怎样判 | 条件定义 + 支持证据（**条目 ID+修订号**【v3.1.1 强化为强制】） |
| 判不出怎么办 | 缺失/冲突/不可读时的处理 |
| 做什么 | 具体动作与产出，**禁止「全面分析」「适当优化」这类空话** |
| 怎样验收 | 检查什么、何时继续/退回/人工复核 |

### 三值判断与未知向后传播

**满足 / 不满足 / 未知**。「没找到支持材料」≠「不满足」，更 ≠「满足」。

【v3.1.1】**未知分级**：无关说明字段的未知（如案例统计口径）不阻塞整体；**判断前提未知**则阻断受依赖结论并传播到交付状态。两类都保留测试（P2）。

未知只暂停依赖该事实的分支，其余继续，输出待补证据清单——但未知**必须向后传播**到依赖该分支的后续节点与**最终交付状态**：

- 必需节点未完成 → 可交付已完成部分或带明确缺口的草稿，**不得标记整体完整通过**
- 交付状态三档：**完整 / 部分（列出已完成与缺口）/ 阻塞（缺什么、怎么补）**

### 最小执行结构（每个 Skill 产物必备）

```
输入要求 → 必需判断节点（先后依赖明确）→ 条件分支（多条件同时满足时的处理顺序、动作冲突处理）→ 汇总检查 → 完整交付 / 有限交付
```

- 简单任务可线性，关键是**有执行关系而非节点集合**——只有节点清单、没有先后/依赖/分支关系的产物不合格
- 完成判定：哪些节点必需、哪些可选；全部必需节点完成后才可标记「完整交付」

## 7. 双门准入与失败分流（第 3 道）

### 双产物契约

| | Wiki | Skill |
|---|---|---|
| 回答 | 知道什么 | 接下来怎么做 |
| 组织 | 围绕主题/问题 | 围绕任务与决策（最小执行结构） |
| 不确定性 | 可展示争议，但明显区分 | 不确定信息不得默认满足执行条件，需有分支 |
| 验收 | 忠实、完整、可解释、可追溯 | 选对路径、读对依据、缺证据走对分支、产出合格 |
| 禁止 | 混入 WorkBuddy 路径/安装/工具调度 | 重复整篇知识解释（保留执行必需的条件限制） |

- Wiki 工作区 `wiki\<主题>\`，审定后归档：能归类 → `4、专利知识库\<工序目录>\wiki\<主题>\`；跨类综合 → `14、外部收集\Wiki\<主题>\`。均附溯源与条目 ID
- **知识分流五去向**：仅进 Wiki / 进案例库 / 成 Skill 候选 / 进待核验区 / 不采纳（记录原因）。不默认「知识最终都要技能化」
- 【v3.1.1】升级顺序强制：发现来源变化 → 比较具体命题 → 更新证据或候选结论 → 评估准入和真实依赖 → 批准知识修订/快照 → 更新 Wiki 与 Skill → 回归。**新核验结果先进入知识条目修订，再生成 Wiki/Skill；产品表格不得单独提级**（F08）

### 双门准入（替代 A 路线一揽子验收）

**第一门 · 知识迁移门**（过了才进条目库与 Wiki）：

1. 依据可定位（能指回 raw 原文）
2. 含义忠实（语义保真零升格零降格，§3）
3. 条件完整（适用边界与六要素可查）
4. 例外保留
5. 版本明确（法条/指南类不混用版本，如不把 2023 指南口径写成现行）

**第二门 · Skill 准入门**（在第一门之上，才进执行型 Skill）【v3.1.1 整体升级：从「字段齐全」升级为「状态读取」】：

6. 可识别的触发条件
7. 必要输入明确
8. 具体动作（禁止空话）
9. 输出定义
10. 验收标准

**11.【v3.1.1】使用资格检查（每个执行节点强制）**：每个执行节点必须引用**具体知识条目修订或批准快照**；检查该修订的：

- **使用资格**：允许解释引用 / 内部策略（经内部决策批准的适用范围）/ 正式动作授权——三者不得混用；「允许解释性展示」的条目不得作默认执行分支（应为「策略说明/候选建议」）；候选/待验证条目只进**预览/试验模式**（显式实验开关），不作默认正式分支
- **适用范围**：节点用途是否落在条目声明的适用边界内
- **关键未知项**：判断前提未知 → 节点输出未知并传播（§6）
- **依据来源**：是否依赖未准入推导或 synthetic 数据（§9 血缘规则）

**12.【v3.1.1】未登记行为禁入产品**：产品中每个关键动作必须能回溯其 KE 依据；复用既有条目 ≠ 允许在产品中补入未登记的新关键行为——发现时补登记条目或从产品移除，二选一。

**13.【v3.1.1】文末免责声明不能替代节点级准入决定**：整页「部分交付」声明不改变单个节点的准入判定。

**概念、原理、背景、争议解释可以止步于 Wiki**——过不了第二门不是失败，是正确分流。

【v3.1.1】**内部策略通道**：内部经验策略不必等外部验证才可用，但须以**明确的内部决策**登记：适用范围、可推翻条件、测试要求、回退方式——批准后方可作限定范围内的默认分支。未走此通道的解释级内容一律不进默认分支。

### 【v3.1.1】四种核验分账（F08）

以下四件事分开记录，不得互相替代或合并升级：

1. **原规则依据核验**（该规则的法规/来源依据本身是否核实）
2. **指定修改影响核验**（某次来源修改是否影响该规则——「本次修改无影响」只关闭此项待办，**不升级第 1 项**）
3. **当前任务适用性**（该规则是否适用于手头任务）
4. **执行准入**（§7 第二门，节点级使用资格）

### 【v3.1.1】快照一致性（F08）

- 一个快照号对应**不可变的 KE 修订集合及证据版本**；改状态/依据/行为必须新修订或新快照，同一快照内 KE/_index/Wiki/Skill 的状态不得互相矛盾
- 发布清单字段：产品版本 / 源哈希 / KE 修订集合 / 批准事件 / 测试记录 / 副本哈希

### 验收失败按原因分流（替代统一降级 B）

| 失败原因 | 去向 |
|---|---|
| 结构不适合（内容对但组织差） | B 路线重组织 |
| 依据缺失 | 待补证据区——**重蒸馏不能凭空修复证据** |
| 历史版本（内容本身过时） | 保留历史属性，查现行适用（如指南 2023→2025） |
| 描述型（本来就是解释/背景） | 进 Wiki |
| 实质错误或冲突 | 核验（第 4 道）或争议处理（§4） |

### 粒度规则

**条目级，不是文件级。** 同一份规则库里可能同时有可靠规则、过时依据、案例观察、未验证建议，不能整份按「移植」处理。归档分类（放哪）与知识分类（被谁用）是两套。

## 8. 测试体系（第 4 道）【v3.1.1 重整】

### 两层测的是不同的对象，不得混用结论

- **第一层 · 蒸馏能力测试**：同批材料，不同版本流水线各处理一次，比较条目质量。比较对象是**流水线版本**。
- **第二层 · 领域 Skill 测试**：用未作示例写入的任务测生成的领域 Skill；无旧版基线时明确标注「无基线」，不虚构对照。比较对象是**领域 Skill**。

### 【v3.1.1】测试证据包最小字段

每条测试记录至少含：**run_id、技能版本与哈希、模型/运行设置、来源快照、输入、期望行为、完整实际输出、判定理由、测试类型、判定方法**。没有运行写「未执行」；手工推演写「推演」；**不把「设计上应通过」记为测试结果**。

### 【v3.1.1】六层测试类型分层与登记口径

静态检查 / 手工推演 / 合成数据测试 / 真实任务运行 / 连接器联调 / 人工复核。

登记规则：**按可取得的证据逐项登记**——已确认未执行的标「未执行」；有明确手工推演记录的标「手工推演」；缺少可复核原始运行记录的标「运行状态未能核实」，**不得仅因缺少记录倒推其从未运行**。两个维度分开：**输入是否合成数据** ≠ **测试是否实际执行**（实际执行的合成用例形成真实测试记录；真实来源材料也可能只做了静态分析）。

### 【v3.1.1】稳定测试 ID 覆盖表（废止集合性「全过」表述）

spec 与 sources 的两套「八情形」统一为一张**稳定测试 ID 覆盖表**（含同源转述、指令注入等情形独立登记 ID）；报告逐项登记，不得以「八情形全过」等集合表述代替。

### 【v3.1.1】重新提取验证（存量修正 ≠ 能力修复）

分析能力类测试（情态逻辑、编码冲突等）**冻结新版蒸馏 Skill，从原始材料重新执行提取与分析**；不得把人工修好的 KE、审计结论或标准答案作为待测输入。分别证明两件事：①存量产物已被修正；②新版 Skill 能从来源重新生成正确结果——前者通过不代表后者通过。

### 【v3.1.1】固定回归集与正向控制

- 实际反例（F01~F07 类）固化为固定测试输入；正向样本（KE-OASIS-006/007、KE-DRW-018 等「案例观察/候选/模式候选」条目）冻结，加强门槛时不得误删
- 未见任务测试（换领域、换表达、删关键证据、加入真实冲突）在固定反例通过后进行；正确答复包括明确的差异和未知
- 问题关闭与测试对应：未完成的验证对应**未关闭或明确延期**的范围，不得最终统一登记「全部关闭」

**验收底线（先于任何综合分数）**：不虚构依据 / 不把建议升格为硬规则 / 不丢关键条件例外 / 不把未知改写为确定 / Wiki 与 Skill 无未解释的语义冲突 / 未知已传播到交付状态。

## 9. 语义化升级（第 5 道）与依赖分支模型

### 变更六分类（分析先行，再动手）

| 变更类型 | 处理 |
|---|---|
| 仅增出处 | 【v3.1.1】默认只登记**新增待核验引用记录**（书目存在性/原文定位/原文支持命题/适用本任务四项分开记录），完成实际定位与读取才允许改变核验状态——**不因新增引用文字自动升级** |
| 补解释案例 | 视需要补参考 |
| 增适用条件 | 查触发与适用判断节点 |
| 发现反例 | **按 §4 反例六情况分类处理**（不是一律缩边界）+ 仅判定需要时建例外分支 + 反例测试 |
| 改变结论效力 | 替代/撤销/历史关系 → **走确认门** |
| 仅措辞变化 | 去重，不改行为 |

【v3.1.1】**分类不预设结果**：来源新版本进入后，保留原分类的历史记录，**按修正后的命题、证据和实际消费者重新判定当前分类**（原「效力变化」可能改判「来源变化+候选新增」，反之亦然）。

【v3.1.1】**增量影响分析强制比较**（F06）：语义变更记录至少含——**旧命题（原条目中的准确原文）、旧证据定位、新命题、新证据定位、被改变的条件/情态/对象、真实受影响消费者（具体 Wiki 段落/Skill 节点）**。找不到旧命题（该命题未进入条目基线）→ 记「来源更新/新增候选/依赖登记缺失」，**不虚构现有 KE 的效力变化**。

【v3.1.1】**synthetic 标记与用途限定**（F03）：全部模拟派生项（条目修订、候选补丁、示例变更单、测试结果）加 `synthetic=true` 标记与独立测试命名空间（S- 前缀）。阻断按用途：

| 情形 | 处理 |
|---|---|
| 用模拟案例/书目证明**领域事实已核实** | 阻断证据升级与相应正式执行准入 |
| **实际运行**合成用例验证**系统行为**（会不会错误升级证据等） | 可作为**该用例范围内**的行为测试证据 |
| 因合成用例通过声称**真实业务效果或连接器联调**通过 | 不允许扩大结论 |

依赖记录区分「**知识依据**」与「**验证证据**」；测试记录区分「**输入来源**」与「**实际执行状态**」。模拟血缘传播：模拟来源 → 模拟条目/修订 → 模拟证据状态 → 模拟产物，测试属性沿依赖链继承，不得中途变成正式状态。正式蒸馏按真实来源从 r1 起重新分类，不以模拟 rN 为基线。

【v3.1.1】**证据升级联动确认门**（F03）：证据状态升级改变执行资格时（如「未核验→已核验」使条目进入默认分支），**重新评估确认门**；不得以「命题文字未改」直接判定不影响行为。

## 10. 【v3.1.3】发布布局与 pre/post 机制（第 6 道）

### 10.1 安装布局与引用闭包

- 暂存包 = **实际安装布局**：运行面 `skill/` `knowledge/` `tools/` `approved/`；历史证据面 `history/`；机制件 `deploy/`；清单 `lock/`。
- 运行必需引用**必须**指向 `C:\Users\<user>\.workbuddy\skills`（安装根解包目录）下的**冻结副本**，或登记为**显式外部依赖**；
  **残留旧开发路径（`patent-distillery\...`、`OneDrive\...\wiki\...` 等）一律为缺陷**，由 `build_stage4.py verify` 阻断。
- 外部可变依赖**不默认不可变**：逐项登记类型 + 检测方式（sha16 / prompt-sha16 / 存在性 / 模式串），pre 阶段实算比对。

### 10.2 批准记录的可核对性（A312-05）

`deploy/pre_deploy.py` 只做**可核对性**检查，并**固定输出**声明：

> JSON 形式合法**不能单独证明人的授权**；本报告只证明批准记录**可核对**。

- 核对项：批准者（非自动化占位）／原始批准引用／范围非空／目标在激活副本区／动作白名单／状态=approved／
  有效期（**无期限不接受**）／候选清单与冻结清单**集合相等**／逐件散列**三方比对**（批准记录 ↔ 冻结清单 ↔ 工作区实算）／线上 prompt 实算复核。
- 通过态文本恒为「批准记录可核对；**部署动作仍须单独批准**」——机制**不产出**「已获授权」结论。

### 10.3 部署后三态（含未部署，A312-06）

`deploy/post_deploy.py` 必须给出**有证据的不同结果**，**不得**把「未部署」或「未做冒烟」记作通过：

| 状态 | 判据 |
|---|---|
| `not_deployed` | 部署根不存在或为空 → 如实登记，**不得为验收先执行未批准的发布** |
| `deployed_ok` | 逐文件与批准清单一致 **且** 收到**本次实际冒烟结果** |
| `deployed_unverified` | 文件一致但**未收到本次冒烟结果** → 不作通过 |
| `deployed_mismatch` | 缺失／不一致／**同目录计划外多余文件**任一命中 |
| `rolled_back` | 冒烟失败且内容与部署前状态**逐文件一致** |
| `rollback_required` | 冒烟失败、尚未（完整）恢复前态 |

### 10.4 T15-v3 真实升级组件（三层登记）

- 升级组件**实际执行**批准判断**再**据此改变绑定；批准/拒绝分支相互独立；旧修订不可变。
- 试验失败由**实际输出**（trial 产出文件）触发回滚，且**保留完整而非截断输出**。
- 三层登记：**沙箱函数层**（可实测）／**真实领域 Skill 层**（需部署后）／**平台联调层**（需连接器事件层授权）。
  **沙箱 ≠ 平台**，不得用沙箱结果充当平台行为证据。

### 10.5 阶段边界（不得互相顶替）

| 阶段 | 完成判据 | 不要求 |
|---|---|---|
| candidate | 结构自洽 + 引用闭包 0 断链 + 机检 + 反向测试 | **不要求发布批准、不要求已部署** |
| 发布 | 批准记录**可核对**（pre）→ 部署 → 逐文件比对 + 实际冒烟（post） | —— |

**不得**把 APPROVAL-BIND / POST-DEPLOY 前移为候选阶段的通过条件，**也不得**因尚未部署而把候选阶段判为未完成。
