# 专利 Skill 蒸馏流水线 v3.2.11（双源 · 双产物）

一句话：从**本地专利知识库 + ima 知识库**取料 → 提炼**可追溯知识条目**（中间层）→ **七动作分析 + 三推理铁则 + 覆盖记录** → **Wiki + Skill 双产物**（双门准入、最小执行结构）→ **语义变更驱动的依赖分支模型升级**。

**衡量标准不是产出多少，而是形成了多少有依据、有边界、能指导判断、可以随新证据修订的知识。**
**核心验收问题：面对不完整、带例外、存在争议或只能有限推广的材料，能否忠实提取、说明支持边界、作出正确的产物分流，并且在新证据进入后有依据地修改既有判断。**

## 六道工序（骨架；每道详细规则在 analysis-spec.md）

### 第 0 步 · 选题定界

写进 `logs\<skill-name>.md`：**输入 / 输出 / 边界**（法律类只出"草稿+依据+人工复核点"），以及**目标知识问题表**（六类，见 spec §1）——此表既指导取料也指导验收，最终报告按四态（已回答/部分回答/资料不足/未读不能判断）作答，并配 §2B 覆盖记录。

### 第 1 道 · 取料

- **只读红线**：按上方「只读三分」执行；外部新知识按类别进对应目录 `外部收集\`（路由表见第 5 道），归不进的进 `14、外部收集\`
- 形态分流：md 直读；docx/pdf/mhtml/xlsx 用 markitdown；yml 读内容提规则；exe/py/zip 不作知识源
- **图像口径（v3.1.1 改能力条件表述）**：图片内容**是否可读取决于能力**——已有可靠静态读取能力时可以使用（独立图片直接读取，文档内图片随文档转换读取）；无能力或内容不可读时**登记未读**；不得静默跳过后仍宣称完整覆盖。「只在图表中的内容是否已读取」记录在条目「图表证据」字段（人工协同读取为当前无自动能力时的降级方案，不等于永远排除）
- 每份原料头部加溯源块（来源+日期 / ima 库+media_id）
- **优先级声明（v3.1）**：成品规则库/规则卡/判断链 > 结构化笔记 > 教材 > 公众号——这只是**取料与处理顺序，不是事实可信度、规范效力或现行适用性的排序**；带规则 ID、已结构化、已生成过 Skill 均不能替代原始依据核验
- **⚠️ 法条前置（claim-drafting 必做）**：本地审查指南 md 为 2023 版，**2025 修改已于 2026-01-01 施行（局令 84 号）**，取料必须先取 2025 修改决定作对照（重点：第二部分第九章第 6 节 AI 章节等）

### 第 2 道 · 知识分析【核心】

**读 `C:/Users/<user>/.workbuddy/skills/patent-skill-distillery/references/analysis-spec.md` §2~§5 后执行。** 禁止从来源文件直接生成 Wiki 或 Skill：

1. 每个关键结论形成**知识条目**（v3.1 模板：中性句式 + 三标签 + 证据状态三子项 + 生命周期，spec §2）
2. **语义保真检查**（spec §3）：零升格零降格
3. **跨源关系分析**（spec §4）：七关系 + 六要素判定 + 反例六情况；两铁则（相似≠重复、来源多≠证据多）
4. 条目登记 `_index.md`（v3.1 四项：稳定 ID / 修订号 / 正反向引用 / 共享条目归属）——**v3.1.3 起 `_index.md` 由 manifest 派生生成（`C:\Users\<user>\.workbuddy\skills\tools\build_index_v313.py`），不手写资格与修订集合**；条目本体的**结构化元数据块**（`ke-meta`：use／scope／deps[purpose,required]／source_synthetic）为机读契约，与命题冲突时**以命题为准**并需当次修好
5. **三种分析对照（v3.1.3 明确；对应三类路线，不得混用）**：
   - **对照一·移植对照（A 路线）**：成品规则 vs **原始来源原文**逐句比对 → 判「可迁移／需重组／依据缺失／历史版本／描述型／实质错误」，**失败按原因分流**，不是统一降级
   - **对照二·重提对照（B 路线）**：原始材料 → 七动作分析 → 条目，**与既有条目/既有答案隔离**（评审答案不得进入待测输入）；同一来源内部须区分**证据四层级**：原始案例/引文 → 作者解释 → 作者归纳 → 模型再解释
   - **对照三·增量对照（C 路线）**：新版本 vs 旧版本，只蒸馏增量；差异落 **六分类**
   三种对照的判据与记录模板见 spec §3/§2A/§9；**同一批次内不得用对照一的结论替代对照二的证据**
6. **读取与错误处理路径（v3.1.3 新增）**：
   - **读取**：按 `KE-ID + rN` **精确修订**读取；按 `use` **按用途**读取；`deps` 的 `purpose`（必要知识／背景解释／验证证据）决定该依赖是否影响本次结论
   - **依赖目标不可解析**（既非 KE-ID 又无 `type:` 显式类型标记）→ **报错并停在构建门前**，不得静默丢弃后宣称「无断链」
   - **正文与 manifest 散列不一致**（漂移）→ 以**实际文件**为准并触发重新构建与回归，**不得**以 manifest 为真、也不得两处各留一份
   - **来源合成性未知（null）** → 按「未知」处理：可作其范围内的**测试证据**，**不得**用于核实外部事实
   - **条目资格不足** → 降级为预览/建议输出或止步 Wiki，**不阻断整批**（护栏不得退化为全部阻断）
7. 原料形态分流三条路线：**A 移植**（带规则 ID 成品）→ **双门准入**（知识迁移门→Skill 准入门，spec §7），失败**按原因分流**（结构不适合→B 重组织；依据缺失→待补证据；历史版本→查现行；描述型→进 Wiki；实质错误→核验，不是统一降级 B）；**B 蒸馏**（原始材料）→ **七动作 + 三推理铁则 + 分析依据摘要**（spec §2A）+ **两类覆盖记录**（spec §2B）；**C 增量**（已有成熟技能）→ 只蒸馏本地特有增量

### 第 3 道 · 双产物生成

**读 spec §6~§7。** 同一组审定条目 → 两个产物：

- **Wiki（解释型）**：回答"知道什么"，围绕主题组织，可展示争议但明显区分；产出后归档（可归类 → 对应工序目录 `wiki\<主题>\`，跨类 → `14、外部收集\Wiki\`）。知库库 LlmWiki 可辅助组织与矛盾标注
- **Skill（执行型）**：回答"接下来怎么做"，**判断节点五要素** + **三值判断**（满足/不满足/未知）+ **最小执行结构**（输入要求→必需判断节点（先后依赖）→条件分支（多条件处理顺序、动作冲突）→汇总检查→完整/有限交付；**有执行关系而非节点集合**，spec §6）
- **机读绑定契约（v3.1.3 新增）**：Skill 产物的节点绑定必须同时给出 ①人读节点绑定表 与 ②`node-bindings` JSON 块（`node/ke/revision/use/mode`），**声明节点须全覆盖、无重复绑定、正文正式动作须全部登记**；发布前由 `audit_v313_validator.py` 的 BINDING-COVERAGE / QUAL-USE 直接核对**实际文件**。仅有人读表格不构成绑定契约。
- **按任务的完成门槛（v3.1.3 新增）**：按**请求类型**确定必需节点与完成条件——规划型/诊断型请求**不要求先取得合格新图**；「QC 失败不得放行」只约束**候选图进入后续提交**，**不阻止**输出不通过报告；输出分栏（材料读取状态／知识依据状态／检查结论／产物可使用程度）；输入分四态（未提供／未读取／不可读／确实不存在）
- **未知向后传播**：未知只暂停依赖分支，但必须传播到依赖该分支的节点与**最终交付状态**——必需节点未完成时可交付部分成果或带缺口的草稿，**不得标记整体完整通过**（交付状态三档：完整/部分/阻塞）
- **知识分流五去向**：仅进 Wiki / 进案例库 / 成 Skill 候选 / 进待核验区 / 不采纳（记录原因）——**概念、原理、背景、争议解释可以止步于 Wiki**，过不了 Skill 准入门是正确分流而非失败
